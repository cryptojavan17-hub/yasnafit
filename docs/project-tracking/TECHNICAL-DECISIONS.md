## TD-01 | SQLite به‌عنوان دیتابیس (local-first)
- **DATE:** 2026-08-22 (نسخه 0.1.0)
- **DECISION:** SQLite تک‌فایلی (`data/yasnafit.db`, WAL) با `node:sqlite` داخلی Node؛ بدون سرور DB جدا.
- **CONTEXT:** محصول باید روی کامپیوتر شخصی مربی بدون نصب و وابستگی اجرا شود.
- **WHY:** صفر-تنظیم، آفلاین، تک‌فایل قابل‌بکاپ؛ مناسب تک‌کاربره محلی. (مستند در ARCHITECTURE.md)
- **ALTERNATIVES:** سرور Postgres/MySQL — نیازمند نصب و نگهداری؛ Hive نسخه Flutter قدیمی — مناسب رابط SQL و یکپارچگی داده.
- **CONSEQUENCES:** مقیاس‌پذیری چندکاربره محدود (طراحی برای سینک آینده)؛ `node:sqlite` هنوز experimental (هشدار رسمی Node).

## TD-02 | HTTP سرور خالص Node به‌جای Express
- **DATE:** 2026-08-22
- **DECISION:** `server.js` با ماژول `http` داخلی؛ روتینگ دستی regex.
- **CONTEXT:** وابستگی حداقلی و کنترل کامل روی امنیت/سرور فایل‌ها.
- **WHY:** بدون node_modules، سطح حمله کمتر، کنترل دقیق کوکی/CSP/سرو فایل خصوصی. (مستند در ARCHITECTURE.md)
- **ALTERNATIVES:** Express/Fastify — راحت‌تر ولی وابستگی و میان‌افزار اضافه.
- **CONSEQUENCES:** روتینگ و بدنه‌پارس باید دستی نگهداری شوند؛ server.js بزرگ شده (~۱۹۰۰ خط) — دین فنی شناخته‌شده.

## TD-03 | لایه سرویس جدا از سرور (layered)
- **DATE:** 2026-08-22
- **DECISION:** منطق دامنه در `src/*-service.js`؛ سرور فقط روتینگ/احراز/سریال‌سازی.
- **WHY:** تست‌پذیری بدون HTTP، جداسازی مسئولیت، آماده‌سازی برای انتقال به سرور مرکزی آینده.
- **ALTERNATIVES:** همه‌چیز در server.js — در نسخه‌های اول همین بود و به سرویس‌ها شکسته شد.
- **CONSEQUENCES:** باید انضباط نگهداری شود (ویژگی جدید = سرویس جدید، نه سرور).

## TD-04 | جدول‌های نرمال‌شده = منبع حقیقت برنامه (نه JSON)
- **DATE:** 2026-08-22 (Critical Issue #1 در ARCHITECTURE.md)
- **DECISION:** `training_programs → program_days → exercise_systems → program_movements → movement_sets` منبع حقیقت؛ `program_data` JSON فقط نمای transport و همیشه از DB بازسازی می‌شود.
- **WHY:** جلوگیری از واگرایی خاموش دو بازنمایی رقیب (JSON در برابر جداول).
- **ALTERNATIVES:** ذخیره JSON واحد — ساده‌تر ولی بدون یکپارچگی رابطه‌ای و پرس‌وجو.
- **CONSEQUENCES:** ذخیره/بارگذاری برنامه همیشه از داخل تراکنش DB می‌گذرد؛ JSON هرگز مستقیم از ورودی نوشته نمی‌شود.

## TD-05 | معماری ID دوگانه (id داخلی + original_id) و هش‌های UI
- **DATE:** 2026-08-22 (Critical Issue #2 و #3)
- **DECISION:** `id` = PK داخلی؛ `original_id` = شناسه دیتاست ۲۷۰۷ تایی (سازگاری ایمپورت)؛ هش‌های پایدار UI (dayHash/…) با قالب `/^[a-zA-Z0-9_-]{4,64}$/` و یکتا.
- **WHY:** رفع ابهام ارجاع‌ها و پایداری شناسه‌ها بین ذخیره/بارگذاری.
- **ALTERNATIVES:** استفاده مستقیم از original_id به‌عنوان PK — خطر تصادم با داده‌های آینده.
- **CONSEQUENCES:** نگاشت fallback در program-service برای داده‌های قدیمی لازم شده است.

## TD-06 | stable_id (UUID) + version + حذف نرم برای آماده‌سازی سینک
- **DATE:** 2026-08-22 (Critical Issue #4 و #5)
- **DECISION:** هر موجودیت sync-relevant: `stable_id` UUID + `version` (هر آپدیت +1) + `deleted_at`.
- **WHY:** شناسه پایدار بین دستگاه‌ها + تشخیص تعارض + حذف بدون شکستن ارجاع‌ها در سینک آینده.
- **ALTERNATIVES:** حذف سخت — با سینک ناسازگار؛ فقط updated_at — تشخیص تعارض ضعیف‌تر.
- **CONSEQUENCES:** همه کوئری‌ها باید `deleted_at IS NULL` را فیلتر کنند؛ حذف سخت فقط داخل تراکنش بازسازی فرزندان برنامه.

## TD-07 | مایگریشن‌های نسخه‌ای idempotent
- **DATE:** 2026-08-22
- **DECISION:** مایگریشن‌های شماره‌دار در `src/migrations.js`؛ جدول `schema_migrations`؛ اجرا تراکنشی (BEGIN/COMMIT/ROLLBACK)؛ رکورد انتشار محصولی هم از همان مسیر ثبت می‌شود.
- **WHY:** ارتقای امن DBهای موجود بدون دست‌کاری دستی + تاریخچه قابل‌ممیزی.
- **ALTERNATIVES:** SQL دستی — بدون تکرارپذیری.
- **CONSEQUENCES:** هر تغییر اسکیما فقط با افزودن مایگریشن جدید (هرگز حذف/بازنویسی).

## TD-08 | تفکیک کامل احراز هویت مربی/شاگرد

## TD-48 | زنجیرهٔ حل‌شوندگی منبع و تصویر rev10: canonical به‌عنوان منبع نهایی + og:site_name + retry «نیازمند پردازش مجدد»
- **DATE:** 2026-09-21 (Correction 10 — T-17)
- **DECISION:** (1) برای هر کاندیدا یک `fetchArticlePage` از صفحهٔ انتشارکنندۀ اصلی: `rel=canonical` **منبع نهایی** است (نه لینک کشف، نه ریدایرکت)؛ گوگل‌نیوز: decode آفلاین → follow هدایت زنده → canonical • (2) نام منبع مربی‌پسند = `og:site_name` صفحهٔ اصلی (نه نام فید) • (3) زنجیرهٔ تصویر دقیقاً: og:image → twitter:image → JSON-LD image → main `<img>` → thumbnail فید (فقط اگر محتوایی باشد) + بلاک‌لیست (گوتگ/گستاتیک/لوگو/آیکون/پیکسل) + ممنوعیت تصویر مشترک بین مطالب متفاوت • (4) متن اصلی مقاله (≤8000 کاراکتر از `<article>`/`<main>`) در پرامپت AI → پیش‌نویس ویرایشی فارسی طبیعی • (5) شکست AI/حل‌شوندگی = internal `needs_reprocess` + retry خودکار ≤۳ در اجراهای بعدی؛ ردیف هرگز در شمارش «آماده بررسی» نیست • (6) `reprocessStaleDrafts` در هر اجرا: پیش‌نویس‌های legacy (انگلیسی/کهن/گوتگ‌نیوز) یا بازپردازش می‌شوند (به‌روزرسانی **همان** مقاله با `updateArticle`) یا رد با دلیل فارسی — صف زنده خودبه‌خود تمیز می‌شود • (7) `queueStats.drafts` = فقط آماده؛ `needs_reprocess` جدا.
- **CONTEXT/WHY:** rev10 صاحب (2026-09-21): در نتیجهٔ واقعی هنوز عنوان انگلیسی خام، تصویر گوتگ تکراری، لینک RSS گوگل‌نیوز و مقالات ۲۰۱/۲۰۲۰ + «۰ جدید» در کنار «۷ آماده» بدون توضیح.
- **ALTERNATIVES:** 1) فقط decode base64 گوگل (rev9) — رد: فرمت‌های واقعی همیشه قابل کدگشایی آفلاین نیستند. 2) حذف پیش‌نویس‌های قدیمی — رد: تخریب‌گر؛ بازرسی+بازپردازش/رد با دلیل صادقانه‌تر است. 3) تصویر thumbnail فید به‌عنوان اول — رد: فیدهای گوتگ‌نیوز thumbnail عمومی مشترک دارند (دقیقاً باگ گزارش‌شده). 4) retry بی‌پایان — رد: سقف ۳ + رد نهایی.
- **CONSEQUENCES:** (1) هر کاندیدای قابل‌رسیدنی یک fetch صفحهٔ انتشارکننده (15s timeout) دارد • (2) بدون شبکه، کاندیدا بدون دادهٔ صفحه پیش می‌رود (source_url همان لینک فید، تصویر فقط از thumbnail معتبر) • (3) دیتابیس‌های زندهٔ قدیمی در اولین اجرای بعدی خودکار پاک‌سازی می‌شوند • (4) ~۱۱۰ چک رگرسیونی + npm test + e2e سبز + اجرای واقعی e2e (canonical/Site Four/تصویر og/متن فارسی منتشرشده).

## TD-49 | ربات تلگرام بدون وابستگی: سرویس داخلی + webhook روی همان سرور (secret مشتق از توکن) + polling فقط برای توسعه؛ هیچ ذخیره‌ای
- **DATE:** 2026-09-21 (Task 29 — پرامپت دوم مالک)
- **DECISION:** (1) ربات به‌عنوان یک سرویس داخلی `src/telegram-bot-service.js` روی همان پروسهٔ `server.js` پیاده شد، با `fetch` داخلی Node و **بدون افزودن `telegraf`/`grammy`/`node-telegram-bot-api`** • (2) پروداکشن = webhook روی `POST /api/telegram/webhook` همین سرور؛ ثبت با `setWebhook` در هر استارت (idempotent) و محافظت با هدر `X-Telegram-Bot-Api-Secret-Token` (مقایسهٔ زمان‌ثابت)؛ راز پیش‌فرض = HMAC-SHA256 از توکن (پایدار، چاپ‌نشدنی) با امکان override از `TELEGRAM_WEBHOOK_SECRET` • (3) توسعه = long polling؛ حالت `auto` اگر webhook ثبت‌شده‌ای ببیند polling را شروع نمی‌کند (فقط `TELEGRAM_BOT_MODE=polling` صریح آن را حذف می‌کند) • (4) پاسخ‌ها: `/start <هر payload>` → متن مالک verbatim (HTML + anchor صریح + دکمهٔ inline)، `/help` و هر پیام خصوصی دیگر → راهنمای کوتاه؛ گروه/کانال نادیده • (5) صفر نوشتن در DB و صفر chat_id در لاگ؛ `activity_log` استفاده نمی‌شود.
- **CONTEXT/WHY:** پروژه هیچ وابستگی npm ندارد و روی Railway با `npm install` خالی build می‌شود؛ یک کتابخانهٔ ربات فقط برای دو دستور، سطح حمله/نگهداری اضافه می‌کرد. دامنهٔ مالک صریحاً «فقط پاسخ به /start، بدون ذخیره» بود. راز مشتق از توکن باعث می‌شود با ست‌کردن فقط دو متغیر (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_URL`) مسیر webhook همچنان محافظت‌شده باشد.
- **ALTERNATIVES:** 1) کتابخانهٔ آماده — رد: وابستگی جدید برای دو دستور، خلاف قاعدهٔ zero-dependency. 2) پروسهٔ جداگانهٔ ربات — رد: Railway یک سرویس/یک Volume دارد؛ پیچیدگی deploy و دو محل log. 3) راز تصادفی در هر استارت — رد: پایدار نیست و با restart نیازمند `setWebhook` قبل از هر درخواست است (رقابت زمانی). 4) پاسخ به پیام‌های غیر `/start` = سکوت — رد: کاربر با جملهٔ خود مالک («برگرد و حسابت رو وصل کن») به ربات برمی‌گردد؛ سکوت گمراه‌کننده است، راهنمای کوتاه صادقانه است. 5) ذخیرهٔ chat_id «برای بعد» — رد: خارج از دامنهٔ صریح مالک و بدون رضایت/سیاست نگهداری (TG-11).
- **CONSEQUENCES:** (1) بدون `TELEGRAM_BOT_TOKEN` هیچ رفتاری تغییر نمی‌کند (مسیر webhook ۴۰۴) • (2) توکن اصلی فقط روی Railway؛ برای لوکال ربات آزمایشی جدا (مستند در `DEPLOYMENT.md` §۱۰) • (3) پذیرش واقعی فقط توسط مالک با ربات زنده ممکن است؛ تست‌های مخزن با Bot API جعلی هستند • (4) فاز B (nonce یک‌بارمصرف روی `/start <payload>`) می‌تواند روی همین `planReply()` سوار شود بدون تغییر transport • (5) پیام تکراری در webhook ممکن است (retry تلگرام بعد از timeout) — برای خوش‌آمد بی‌ضرر است؛ برای outbox آینده dedup با `update_id` لازم است (طرح مرحلهٔ C ممیزی).
