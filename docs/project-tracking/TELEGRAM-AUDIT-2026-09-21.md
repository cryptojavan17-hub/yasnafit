## نتیجهٔ اصلی

**بخش موجود، فرم ثبت آیدی و بازکردن لینک است؛ یک ربات یکپارچه با اتصال تأییدشده و ارسال برنامه نیست.**

در کد این مخزن، دریافت Update، پردازش `/start`، فراخوانی Bot API، ذخیرهٔ `telegram_user_id`/`chat_id`، تأیید مالکیت حساب و صف ارسال پیدا نشد. نام کاربری ربات در تنظیمات، به‌تنهایی این قابلیت‌ها را فعال نمی‌کند. وجود احتمالی ربات یا سرویس جداگانه بیرون از مخزن بررسی و تأیید نشده است.

**تصمیم پیشنهادی:** تا اتصال امن و تأیید هویت دوطرفه پیاده نشده، از این آیدی‌ها برای ارسال برنامه یا اطلاعات خصوصی استفاده نشود. دادهٔ فعلی «اظهار کاربر» است، نه هویت تأییدشده. در ممیزی هیچ نشت واقعی برنامه یا ارسال واقعی تلگرام مشاهده نشده؛ مسیر ارسال در مخزن موجود نیست.

**بررسی مدل دوم:** هنوز انجام نشده است. ابزار ارجاع مستقیم به مدل مستقل در این محیط در دسترس نبود. فایل [دستورکار مدل دوم](TELEGRAM-SECOND-REVIEW-HANDOFF.md) آمادهٔ انتقال است؛ این گزارش نباید به‌عنوان اجماع دو مدل معرفی شود.

## ساختار موجود

```text
دکمهٔ عمومی «ربات تلگرام»
  → landing.js: نمایش فرم آیدی
  → GET /api/telegram-bot: آیدی خودِ حساب + نام کاربری ربات
  → POST /api/telegram-bot/connect
      → INSERT telegram_bot_connections
      → اگر نشست شاگرد موجود بود: UPDATE students.telegram_id

کارت تلگرام پروفایل شاگرد
  → PUT /api/student/profile
  → فقط UPDATE students.telegram_id
  → پیام «اتصال ... به‌روزرسانی شد»؛ بدون بازکردن ربات

تنظیم مربی
  → /coach/magazine، تنظیمات سایت
  → settings['site.telegram_bot_username']
```

## یافته‌ها و اولویت اصلاح

### TG-01 — P1: چرخهٔ واقعی ربات پیاده نشده

**وضعیت:** `NOT IMPLEMENTED` در مخزن؛ سرویس بیرونی `NOT VERIFIED`.

هیچ مسیر دریافت پیام، احراز webhook، polling، دریافت هویت ربات، فرمان راهنما/شروع، ارسال برنامه، وضعیت تحویل یا مدیریت قطع ارتباط موجود نیست. پاسخ `200 {ok:true, bot_username:null}` حتی بدون تنظیم نام ربات دریافت شد. این پاسخ فقط موفقیت ثبت را می‌رساند؛ متن‌های رابط می‌توانند انتظار اتصال و ارسال برنامه ایجاد کنند.

**اقدام:** وضعیت‌های «تنظیم نشده»، «آمادهٔ شروع»، «در انتظار تأیید»، «متصل»، «قطع‌شده» جدا شوند. فقط پس از شواهد معتبر وضعیت «متصل» نمایش داده شود. کلید ربات هیچ‌وقت در `site.*` یا پاسخ عمومی قرار نگیرد.

### TG-02 — P1: آیدی متنی مبنای اتصال امن نیست

**شواهد:** `server.js:3436–3444`؛ `src/migrations.js:1442–1449`. دو حساب آزمایشی یک آیدی یکسان ثبت کردند. لینک مرورگر فقط `https://t.me/yasnafit_audit_bot` بود و شناسهٔ درخواست اتصال همراه نداشت.

این رفتار امروز معادل تصاحب حساب نیست؛ ولی اتصال آینده با lookup نام کاربری می‌تواند دادهٔ خصوصی را به حساب اشتباه وصل کند. شناسهٔ سایت ناشناس هم به حسابی متصل نمی‌شود. آیدی اختیاری و قابل‌تغییر را نباید کلید امنیتی گرفت؛ ساختار Chat شناسهٔ مستقل و username اختیاری دارد. [2](https://core.telegram.org/bots/api)

**اقدام:** درخواست اتصال وابسته به نشست فعلی، توکن تصادفی یک‌بارمصرف، ذخیرهٔ هش، انقضای کوتاه، دریافت هویت از Update معتبر در گفت‌وگوی خصوصی و تأیید نهایی صاحب حساب. پارامتر `start` برای چنین اتصال‌هایی پیش‌بینی شده است؛ سقف آن 64 کاراکتر است. [4](https://core.telegram.org/bots/features)

**مهم:** رکوردهای قدیمی نباید خودکار «تأییدشده» مهاجرت داده شوند. مهمان می‌تواند گفت‌وگوی عمومی با ربات را باز کند، نه برنامهٔ خصوصی را با ادعای یک username دریافت کند.

### TG-03 — P1: مسیر اتصال فاقد کنترل مبدأ و نوع محتوا است

**شواهد:** `server.js:3433–3445` در مقایسه با `server.js:1773–1776`؛ `readBody` در `server.js:114–141`.

- درخواست اتصال با Origin نامعتبر و کوکی آزمایشی: **200**؛ همان تغییر از مسیر پروفایل: **403**.
- JSON با `Content-Type: text/plain` نیز **200** و ثبت شد.
- مرورگر واقعی از یک پورت دیگر همان `127.0.0.1`، با کوکی Strict، آیدی پروفایل را تغییر داد. پاسخ به علت سیاست مرورگر قابل‌خواندن نبود؛ نوشتن سرور با این حال انجام شد.

**محدودیت ادعا:** این آزمایش same-site/cross-origin است؛ اثبات ارسال کوکی Strict از یک سایت خارجی نامرتبط نیست. Strict بخشی از خطر cross-site را کاهش می‌دهد، اما جای کنترل مبدأ endpoint را نمی‌گیرد. درخواست ناشناس برای پرکردن جدول هم به کوکی نیاز ندارد.

**اقدام:** کنترل مبدأ برای تغییرات مرورگری، قرارداد JSON صریح، محدودیت اندازهٔ کوچک‌تر برای این endpoint و تست‌های مشابه مسیر پروفایل. webhook آینده نباید به گارد نشست مرورگر متکی شود؛ گارد مستقل خود را لازم دارد.

### TG-04 — P1: نوشتن عمومی بدون محدودسازی و رشد بدون سیاست نگهداری

**شواهد:** در مسیر اتصال فراخوانی `rateLimit` نیست؛ هر درخواست یک INSERT است. در آزمون محدود، 160 درخواست ناشناس با 8 worker، همگی **200** شدند و 160 رکورد ساختند. سه درخواست تکراری هم سه رکورد ساختند. نه TTL و نه مصرف‌کننده/پاک‌ساز برای جدول یافت شد.

**اثر:** ظرفیت سوءاستفاده برای انباشت داده و فشار روی SQLite مشترک؛ اختلال تولید یا سقف ظرفیت در این ممیزی اثبات نشده است. تکرار event ممکن است برای گزارش تلاش‌ها مطلوب باشد، اما باید از «اتصال فعال» جدا و دارای retention باشد.

**اقدام:** محدودیت ترکیبی حساب/IP با تنظیم صحیح proxy، backoff رابط، idempotency درخواست اتصال و نگهداری محدود رویدادها. در حالت تنظیم‌نشده، بی‌دلیل آیدی شخصی ذخیره نشود. برای این اندازهٔ برنامه، ابتدا امکانات موجود؛ افزودن Redis بدون نیاز اندازه‌گیری‌شده پیشنهاد نمی‌شود.

### TG-05 — P2: اعتبارسنجی و نرمال‌سازی ناسازگار

**شواهد اجرایی:** شیء JSON به `[object Object]` تبدیل و ذخیره شد؛ عدد، boolean، `bad name`، متن فارسی و URL پذیرفته شدند. ورودی ` @audit_demo ` به `@audit_demo` در جدول تبدیل شد، چون حذف `@` قبل از trim است؛ در حساب می‌تواند پیشوند اضافی تولید کند. فقط خالی و طول بیشتر از 64 در مسیر عمومی رد شدند.

مسیر پروفایل سقف 100 و کنترل نوع string دارد، ورودی UI پروفایل سقف 99 و فرم عمومی سقف 64 دارد. تنظیم نام ربات نیز `not a bot/url` را پذیرفت و بازگرداند. برای نام کاربری معمول ربات، مستند رسمی الگوی نام و پسوند `bot` را مشخص می‌کند. [4](https://core.telegram.org/bots/features)

**اقدام:** یک تابع مشترک برای parsing/normalization، نوع صریح رشته، تفکیک username نمایشی از شناسهٔ عددی معتبر Telegram؛ تنظیمات ربات با اعتبارسنجی و در مرحلهٔ راه‌اندازی با هویت واقعی ربات تطبیق داده شود. URL/متن دلخواه نباید username تلقی شود. این یافته به‌تنهایی اثبات XSS یا SQL injection نیست.

### TG-06 — P2: ثبت اتصال و ویرایش حساب اتمیک نیستند

**شواهد:** با trigger خطا در UPDATE فقط روی دیتابیس موقت، API **500** داد؛ حساب تغییر نکرد ولی **یک ردیف اتصال باقی ماند**. INSERT و UPDATE در `server.js:3440–3442` تراکنش مشترک ندارند.

**اقدام:** مرز تراکنش مشخص برای اتصال تأییدشده و تغییر حساب؛ اگر جدول فقط گزارش تلاش است، وضعیت success/failure و معنی آن صریح باشد. هیچ مصرف‌کننده‌ای نباید هر ردیف آن را اتصال موفق بداند. تست fault injection بعد از اصلاح به تست invariant تبدیل شود.

### TG-07 — P2: دو مسیر رابط با معنی متفاوت و وعدهٔ نادرست

کارت پروفایل هنوز موجود است. در مرورگر، کلیک دکمه فقط `PUT /api/student/profile` با پاسخ **200** انجام داد، آیدی ذخیره شد، ردیف اتصال اضافه نشد و صفحه روی پروفایل ماند. در حالی که متن کارت از ارسال برنامه و پیشرفت توسط ربات می‌گوید.

**اقدام:** یک منبع وضعیت اتصال و یک سرویس مشترک؛ فرم تماس اجتماعی از «اتصال تأییدشده ربات» جدا شود. مستندات قدیمی که حذف این کارت را اعلام کرده‌اند، مبنای تصمیم نباشند.

### TG-08 — P2: نبود مسیر جایگزین هنگام بازنشدن تلگرام

**شواهد:** `public/landing.js:272–276`. `window.open` بعد از await اجرا می‌شود، نتیجه/وضعیت ناوبری بررسی نمی‌شود و فرم پس از 1400ms بسته می‌شود. در شبیه‌سازی popup مسدود، همچنان پیام «برنامه تلگرام باز می‌شود» نمایش داده شد و تعداد لینک جایگزین **0** بود.

**محدودیت:** وقوع خودکار popup blocking روی مرورگر/موبایل واقعی مالک آزمایش نشده؛ رفتار برنامه در صورت این شکست، آزمایش شده است. `noopener` هم باعث می‌شود اتکا به مقدار برگشتی `window.open` به‌تنهایی تشخیص قابل‌اعتمادی نباشد.

**اقدام:** لینک واقعی و قابل‌کلیک «بازکردن ربات» همیشه در نتیجه بماند، امکان کپی لینک وجود داشته باشد؛ موفقیت ثبت با بازشدن اپ و اتصال واقعی یکی نشود. در قطع شبکه، timeout و امکان تلاش دوباره با دادهٔ حفظ‌شده ارائه شود.

### TG-09 — P2: پاسخ دیررس، ورودی تازه را بازنویسی می‌کند

**شواهد:** `public/landing.js:252–257`. پاسخ GET پیش‌پرکردن در آزمون مرورگر نگه داشته شد؛ کاربر مقدار جدید تایپ کرد؛ پس از آزادشدن پاسخ، آیدی قبلی جای مقدار تازه نشست.

**اقدام:** فقط ورودی دست‌نخورده را prefill کن؛ درخواست در بستن پنجره لغو یا نادیده گرفته شود. ثبت نباید با پاسخ کهنه رقابت کند.

### TG-10 — P2: مدیریت ناقص فوکوس و دسترس‌پذیری

**شواهد:** فرم `role=dialog` و `aria-modal=true` دارد، ولی در Chromium با Tab فوکوس به پس‌زمینه رفت و پس از Escape به دکمهٔ بازکننده برنگشت. ورودی label صریح فارسی ندارد و placeholder جای آن را گرفته است. محافظت کامل اسکرول پس‌زمینه در این بخش دیده نمی‌شود.

**نکتهٔ مثبت:** در viewport برابر 390×844، پنجره با عرض 350 داخل صفحه ماند و overflow افقی سند صفر بود. این تأیید مرورگر در اندازه موبایل است، نه آزمون دستگاه واقعی یا صفحه‌کلید موبایل.

**اقدام:** استفاده از الگوی dialog بومی و مدیریت فوکوس مشابه اصلاح اخیر ویرایشگر مقاله؛ label واقعی، حفظ فوکوس، قفل پس‌زمینه و آزمون Tab/Shift+Tab/Escape و صفحه‌کلید مجازی.

### TG-11 — P2: لغو اتصال، رضایت، audit و نگهداری داده تعریف نشده

**شواهد:** پاک‌کردن آیدی در پروفایل موفق بود، اما 6 رکورد آزمایشی مرتبط در جدول باقی ماند. مسیر مستقلی برای revoke اتصال تأییدشده یا opt-out ربات نیست؛ پس از درخواست‌های اتصال بررسی‌شده، تعداد رویدادهای `audit_events` اضافه‌شده **0** بود. جدول اتصال خود یک ثبت حداقلی دارد، ولی هویت تأییدشده، نتیجه، ابطال و نسخهٔ اتصال را ثبت نمی‌کند.

**اقدام:** حذف فیلد تماس با لغو پیوند ربات یکی نباشد. وضعیت opt-in/opt-out و توقف ارسال‌های معلق، retention محدود و audit کمینه بدون پیام خصوصی/توکن مشخص شوند. ارسال عکس‌های بدن و اطلاعات پزشکی به تلگرام نباید پیش‌فرض باشد؛ اعلان کوتاه با لینک امن به سایت انتخاب کم‌ریسک‌تری است.

### TG-12 — P3: هزینهٔ اضافی مسیر داغ و نبود سنجهٔ ربات

**شواهد:** هر درخواست تلگرام `publicSiteInfo → getSiteSettings` را صدا می‌زند و همهٔ کلیدهای `site.%`/`magazine.%` را می‌خواند؛ فقط نام ربات لازم است. resolve نشست در GET احراز‌شده نیز `last_seen_at` را می‌نویسد. SQLite همگام و مشترک با بقیهٔ سامانه است.

**اقدام:** بعد از بستن خطرهای P1، تنظیم لازم به‌صورت هدفمند خوانده شود؛ کاهش write نشست فقط با رعایت semantics مشترک و تست. زمان پاسخ HTTP، سن آخرین Update، backlog، تلاش ارسال، خطای دائمی و وضعیت ارتباط ربات جدا اندازه‌گیری شوند. گلوگاه شدید یا نیاز به بازنویسی معماری با دادهٔ فعلی ثابت نشده است.

## کارایی اندازه‌گیری‌شده

محیط: Linux x64، Node `v22.22.3`، دیتابیس موقت WAL، loopback، یک نمونهٔ محدود؛ بدون TLS و بدون تماس با Telegram. زمان‌بندی سایر کارهای سندباکس قابل‌کنترل نبود.

| سنجه | تعداد | p50 (ms) | p95 (ms) | بیشینه (ms) |
|---|---:|---:|---:|---:|
| GET عمومی، متوالی پس از warm-up | 40 | 1.09 | 1.46 | 2.88 |
| POST ناشناس، هم‌زمانی 8 | 160 | 7.91 | 16.03 | 35.57 |
| health هم‌زمان با POSTها | 40 | 4.62 | 15.63 | 16.19 |

کل نمونهٔ هم‌زمان حدود **219.17ms** طول کشید. همهٔ POSTها 200 بودند. مجموع اندازهٔ فایل DB/WAL/SHM از **3604816** به **5979640** بایت رسید؛ این عدد رشد پایدار هر ردیف نیست و نباید به حجم روزانه تعمیم داده شود.

**برداشت:** مسیر ذخیرهٔ ساده در این نمونه کند نبود؛ اما هیچ محدودیتی جلوی ثبت تکراری را نگرفت. از این اعداد نمی‌توان توان ارسال پیام، تعداد کاربران قابل‌پشتیبانی، تأخیر تلگرام، مصرف CPU/RAM در تولید یا SLA استخراج کرد. برای آن‌ها هنوز مسیر واقعی ربات و آزمون مستقل لازم است.

## نقاط مثبت قابل حفظ

- نوشتن آیدی با query پارامتری است؛ نشانه‌ای از SQL injection در این مسیر دیده نشد.
- حساب مقصد از نشست استخراج می‌شود، نه `student_id` ارسالی کاربر.
- GET آیدی، فقط اطلاعات همان نشست را برگرداند؛ مهمان آیدی حساب‌ها را دریافت نکرد.
- پاسخ‌ها `Cache-Control: no-store` دارند؛ کوکی نشست HttpOnly و SameSite=Strict است.
- API تنظیمات مربی برای مهمان **401** داد.
- JSON شکسته **400** و متد نامجاز **405** دادند.
- بازکردن لینک `noopener` دارد؛ نبود fallback به معنی بی‌حفاظ‌بودن opener نیست.
- طرح کلی سبک Node/SQLite با اندازه فعلی سازگار است؛ مشکل اصلی، فقدان قرارداد اتصال و چرخهٔ ارسال است، نه انتخاب فریم‌ورک.

## طرح ارتقای حداقلی پیشنهادی — هنوز اجرا نشده

### مرحله A: صداقت رابط و بستن ورودی‌ها

TG-03 تا TG-10، بدون فعال‌کردن ارسال: کنترل مبدأ، قرارداد ورودی واحد، محدودیت درخواست، اتمیک‌بودن، label/فوکوس، prefill ایمن، لینک جایگزین و وضعیت غیرگمراه‌کننده. تست‌های امنیتیِ انتظار ردشدن به سوئیت عادی اضافه شوند؛ اسکریپت مشاهدهٔ فعلی معیار قبولی امنیتی نیست.

### مرحله B: پیوند امن حساب، بدون بازنویسی احراز هویت

- افزودن سرویس کوچک اتصال و جدول‌های افزودنی برای درخواست پیوند و پیوند تأییدشده؛ جدول‌ها و فیلدهای قدیمی تماس حذف نشوند.
- ساخت nonce تصادفی، مثلاً 32 بایت base64url، هش در DB، زمان انقضای پیشنهادی 5 دقیقه و مصرف یک‌باره در تراکنش. این TTL تصمیم پیشنهادی محصول است، نه الزام Telegram.
- ارسال nonce با `?start=`؛ دریافت `message.from.id` و `chat.id` فقط از Update معتبر و private chat؛ متن ادعایی/پیام forwardشده مدرک مالکیت نیست. سازوکار deep link رسمی این پارامتر را پشتیبانی می‌کند. [4](https://core.telegram.org/bots/features)
- تأیید نهایی در نشست اصلی سایت، برای کاهش خطر اشتراک‌گذاری ناخواستهٔ لینک؛ nonce و نشست خام در log ذخیره نشوند. تعارض اتصال و تغییر حساب، رفتار صریح و قابل لغو داشته باشد.
- هویت عددی Telegram به‌عنوان دادهٔ مستقل ذخیره شود؛ از integer سی‌ودوبیتی/عملیات bitwise استفاده نشود. مستند API برای Chat.id تا 52 بیت معنادار را توضیح می‌دهد. [2](https://core.telegram.org/bots/api)
- توکن ربات فقط در secret محیط اجرا؛ هیچ کلید خصوصی در تنظیمات عمومی یا گزارش‌ها. در چت از مالک درخواست توکن نشود.

### مرحله C: دریافت Update و ارسال محدود و قابل‌پیگیری

- برای نصب local-first، long polling گزینهٔ اولیهٔ کم‌زحمت است؛ برای استقرار HTTPS دائمی، webhook گزینهٔ دیگر. مدل دوم باید بر اساس محیط واقعی، یک حالت فعال را مشخص کند؛ هم‌زمان‌کردن بدون طراحی درست یا حذف updateهای pending برای رفع خطا مجاز نباشد.
- در حالت webhook، بررسی `X-Telegram-Bot-Api-Secret-Token` مطابق پشتیبانی رسمی Telegram، محدودیت اندازه و ورودی، ثبت پایدار و dedup بر اساس هویت ربات/`update_id` قبل از acknowledge. [3](https://core.telegram.org/bots/api)
- در polling، ذخیرهٔ cursor پس از ثبت پایدار، جلوگیری از چند poller و بازیابی پس از restart.
- اتصال اعلان‌های موجود به outbox در SQLite، نه HTTP مستقیم داخل تراکنش انتشار برنامه؛ در ابتدا فقط اعلان کوتاه، نه کپی اطلاعات حساس.
- outbox با event key یکتا، زمان تلاش بعد، lease/بازیابی restart و وضعیت ارسال. هنگام ارسال، مالکیت فعال و نسخهٔ پیوند دوباره بررسی شود؛ لغو اتصال باید ارسال معلق را متوقف کند.
- سیاست پیشنهادی برای timeout و خطا: backoff محدود، رعایت `retry_after` در خطای کنترل نرخ، جداسازی خطای دائمی از موقت و وضعیت «نتیجه نامعلوم» برای قطع ارتباط حین ارسال. پاسخ‌های Bot API ممکن است اطلاعات retry را در parameters داشته باشند. [4](https://www.conferbot.com/errors/telegram)
- **وعدهٔ exactly-once سرتاسری ندهید:** dedup داخلی به‌تنهایی ثابت نمی‌کند Telegram پس از timeout پیام اول را ارسال نکرده است. پیام تکراری و ارسال نامعلوم باید در آزمون و UI لحاظ شوند.
- کنترل‌های راه‌اندازی/وضعیت و ارسال آزمایشی فقط مربی؛ `/start`، `/help` و توقف/لغو اتصال با پاسخ فارسی. عدم دسترسی شاگرد دیگر و عدم ارسال خصوصی به گروه الزام پذیرش باشد.

### مرحله D: پذیرش واقعی جداگانه

یک ربات آزمایشی تحت کنترل مالک و دو حساب آزمایشی؛ تنظیم secret از محیط اجرا، نه چت. هویت ربات، دریافت `/start`، تأیید پیوند، ارسال اعلان، جلوگیری از دسترسی حساب دیگر، restart، قطع شبکه، لغو اتصال و نمایش وضعیت بررسی شوند. فقط پس از ثبت این شواهد می‌توان «اتصال و ارسال واقعی» را تأیید کرد. این مرحله در ممیزی حاضر انجام نشده است.

## ماتریس آزمون موردنیاز مدل دوم

| گروه | شرط پذیرش |
|---|---|
| ورودی | شیء/boolean/URL/کاراکتر نامعتبر رد؛ نرمال‌سازی در همهٔ UIها یکسان |
| امنیت درخواست | مبدأ نامجاز رد؛ JSON صریح؛ محدودیت نرخ؛ مالکیت از نشست |
| پیوند | معتبر/منقضی/بازپخش/هم‌زمان/تعارض/nonce اشتراک‌گذاری‌شده؛ قدیمی‌ها unverified |
| هویت تلگرام | بدون username، تغییر username، private در مقابل group، شناسهٔ بزرگ |
| Update | تکراری، خارج از ترتیب، ورودی بد، secret غلط، crash قبل/بعد از persist |
| ارسال | موفق، timeout مبهم، rate-limit، blocked، لغو اتصال حین صف، retry بعد از restart |
| داده | rollback در خطا، عدم ارسال به حساب دیگر، retention، حذف/ابطال و audit بدون راز |
| رابط | popup مسدود، خطای شبکه، prefill دیررس، Tab/Escape/بازگشت فوکوس، موبایل/کیبورد |
| یکپارچگی | حفظ TOTP مربی، احراز شاگرد، برنامه‌ساز، مجله و اعلان‌های داخلی |
| پذیرش زنده | گزارش واقعی دریافت/ارسال؛ fixture و موفقیت HTTP سایت جای آن نیست |

## بازتولید و تحویل به مدل دوم

```sh
node scripts/audit-telegram.js
```

برای آزمایش مرورگر، Playwright و Chromium باید جداگانه در محیط توسعه در دسترس باشند؛ وابستگی تولید اضافه نشده:

```sh
node scripts/audit-telegram.js --browser
```

`YASNAFIT_BROWSER_EXECUTABLE` مسیر مرورگر اختیاری است. نتیجه در `logs/telegram-audit.json` تولید می‌شود. اسکریپت URL مقصد دریافت نمی‌کند، فقط سرور موقت خودش را آزمایش می‌کند و پس از پایان آن را می‌بندد. بخش مرورگر برای بازتولید ایرادِ نسخهٔ بررسی‌شده است؛ پس از اصلاح، باید به تست انتظار رفتار صحیح تبدیل شود و حفظ آن ایراد شرط قبولی نیست.

بستهٔ مدل دوم: این گزارش + `TELEGRAM-SECOND-REVIEW-HANDOFF.md` + JSON شواهد + کد همان کامیت. هیچ credential یا دیتابیس واقعی نباید در بسته قرار گیرد.
