### Owner spec — `@yasnafitbot` answers `/start` (Task 29: welcome message + registration link; webhook or polling; nothing stored)
- **Why:** the landing button (previous entry) opens `https://t.me/yasnafitbot?start=landing`, but a bot only greets when some server answers its updates. The owner's second spec asked for exactly that and nothing more: reply to `/start` / `/start landing` with a fixed Persian welcome that sends the guest to `https://yasnafit.ir/student/register`; add `/help`; **do not** store chat_id/username, link accounts, send notifications or build one-time deep links (later T-20 phases).
- **New service `src/telegram-bot-service.js` (zero dependencies — global `fetch`, Node ≥ 22; no `telegraf`/`node-telegram-bot-api` added):** `getConfig()` reads `TELEGRAM_BOT_TOKEN` (bot is fully off without it), `TELEGRAM_BOT_MODE` (`auto` | `webhook` | `polling` | `off`), `TELEGRAM_WEBHOOK_URL`, optional `TELEGRAM_WEBHOOK_SECRET`, `TELEGRAM_API_BASE` (tests), `YASNAFIT_PUBLIC_URL` (default `https://yasnafit.ir`). `planReply()` is pure: private-chat `/start <anything>` → owner's welcome text verbatim (HTML parse mode, explicit `<a>` on the register URL, inline button «ثبت‌نام در سایت», no link preview); `/help` and any other private message → a short guide with the same link (never silent); groups/channels/edited messages/bots → ignored. `createBot()` runs it: `getMe` + `setMyCommands` at start, then **webhook** (`setWebhook` with `secret_token` + `allowed_updates:["message"]`) or **long polling** (`getUpdates` timeout 30 s, offset advance, exponential backoff, 409 hint, anti-hot-spin guard).
- **Route `POST /api/telegram/webhook` (server.js, before the coach gate):** 404 unless the bot runs in webhook mode, 405 for non-POST, 403 unless `X-Telegram-Bot-Api-Secret-Token` matches (SHA-256 + `timingSafeEqual`), 400 on invalid JSON, otherwise 200 at once and the update is processed afterwards (Telegram retries non-2xx, which would only duplicate greetings). Body size stays under the global 1 MB `readBody` cap.
- **Secret handling:** the token is read only inside the service, never logged (every log/error line passes through `redact()`, including fetch errors whose URL embeds the token). The webhook secret defaults to an HMAC-SHA256 derived from the token (64 hex, stable across restarts, never printed) so the route is protected even when only token + URL are configured; `TELEGRAM_WEBHOOK_SECRET` overrides it.
- **Safety for two environments:** in `auto` mode without `TELEGRAM_WEBHOOK_URL` the bot would poll, but it first asks `getWebhookInfo` and **refuses to poll if a webhook is registered** (that webhook is presumably production); only an explicit `TELEGRAM_BOT_MODE=polling` deletes it. Documented advice: production token only on Railway, a second BotFather test bot for local runs.
- **Observability:** `GET /api/health?detailed=1` (coach-only) now carries `telegram_bot` (`mode`, `running`, `username`, `updates_received`, `replies_sent`, `last_error`, no token/chat ids); startup log lines `[Telegram] bot identity confirmed: @…` / `webhook registered at …` / `disabled — TELEGRAM_BOT_TOKEN is not set`. New operator tool `scripts/telegram-webhook.js` (`info` = `getWebhookInfo` incl. `last_error_message`, `set`, `delete`, `me`, `commands`) reads the token from the shell environment only.
- **Docs:** `DEPLOYMENT.md` §2 (env table) + new §10 (modes, Railway variables, why the webhook is *not* registered in BotFather, manual registration, verification steps, troubleshooting table); `README.md` one-liner.
